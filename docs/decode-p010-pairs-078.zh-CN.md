# Decode Stack 0.7.8-test1：完整十位 P010 解包优化

本项对应 P1/P5 中仍必须执行的 NV15→P010 转换，适用于 GPU 纹理、显式 P010 等
需要标准十位输出的消费者。既有 0.7.6 原生 NV15 显示路径已省掉的转换不重复计入。
独立 `p010_pairs` 默认关闭，依赖 `codec2_sdk_next` 和 `p010_fast`，启用和关闭均需重启。
最终专项结果见 [结构化验收](validation/decode-p010-pairs-078.json)。

## 改动及来源

新代码是对项目既有 MIT `RKPacked10.h` 的本地优化，固定 Khadas Codec2 基线
`e3c30156793f778541b6eaec54ac2a1ac0f6a70c` 及已验收补丁保留。
没有新的直接上游回移，不把它表述为更新整个 SDK、libyuv、RGA 或内核。
选择本地适配是因为现有必需转换路径、缓存布局和 API32 ABI 已明确，其他平台的
十位格式解包不能仅凭格式名称直接用于 NV15。

NV15 连续打包的十位样本仍完整映射到 P010 高十位。新 NEON 行函数直接查表得到
相邻字节构成的半字向量，减少原来的扩宽、拼接及分开的移位操作。
每 16 个样本的两个重叠查表窗口严格限制在原 20 个输入字节内，不越过末行。
尾部仍用原标量函数；缓存行暂存和逐行 memcpy、mapper 布局、CPU/DMA 同步及 fence
均保留，不改变缓冲个数、参考帧、源帧率、分辨率、压缩请求或播放器统计。

补丁：`magisk-codec2-sdk-next/patches/p010-pairs.patch`；
可重建行函数和边界测试在 `tools/pixel-conversion/`。
核心构建器同时校验新旧规范头文件。开关在 Codec2 实例创建时读取；关闭后恢复
此前完整精度转换，关闭任一依赖保留子项选择但抑制生效。

## 验收范围

缓存内存微基准按 720p、1080p、4K，每尺寸 8 组交替旧／新执行顺序，逐字节比较
完整输出。它只筛选候选，不代替真实 Codec2/mapper 路径或通用 FPS 验收。
ARM32/ARM64 均执行 140 组新行函数及标量对照，覆盖所有十位值、宽度尾部、步长、
未对齐输出、保护页、填充不变和无效参数；旧头文件未修改。

实际性能需在同一片源、配置和环境下测量原服务 CPU 用时、真实完整帧数及交付稳定性。
MediaCodec 报告的 opaque `color-format` 不能单独证明实际缓冲是 P010，需结合原生
逐样本回读和配置路径。HDR 要覆盖显式 P010，以免只验到不经过转换的 NV15 原生路径。

本轮保留 Frame Guard 固定 60Hz 和原有 ExoPlayer 黑屏规避；Mali、boot、游戏配置
和外部 Zygisk 设置均不属于本改动。实验安装包字节应与实机验证一致，包内候选状态
由最终验收附录补充。私有地址、原始日志、影片、APK、密钥、原厂库和 boot 不进入交付。


## 新版本实机结果

| 实际状态 | 360 帧 Codec2 服务 CPU 累计用时（秒） | 超过 20ms 的交付迟到 | 回调间隔 P95 |
| --- | --- | --- | --- |
| 原 0.7.7 | 3.96／3.75 | 0 | 33.334ms |
| 新核心开启 | 3.11／3.1 | 0 | 33.334ms |
| 新核心关闭并重启 | 3.83／3.85 | 0 | 33.334ms |
| 再次开启并重启 | 3.17／3.13 | 0 | 33.334ms |

新核心关闭态中位数 3.84 秒，开启及重新启用中位数 3.12 秒，服务 CPU 用时减少约 18.7%。每次源跨度 11.966666 秒，360 输入／输出帧、完整 EOS／停止，共 8 次 2,880 帧。只是限定实际转换路径的 CPU 工作量下降，不推算通用 FPS 或物理显示延迟。

新核心四组 UHD 回读各 3 帧：显式 P010 梯度、GPU 纹理 P010、显式 P010 普通片源、
NV15 原生旁路，共 149,299,200 个样本与独立软件参考完全一致，91,749,915 个样本
低两位非零。两 ABI 的新行函数 140 组边界／精度检查及真实同步等待保留。

原生显示的 PQ/HLG/SDR 分别 100/190/100 帧、暂停/seek/flush/EOS、HDMI 十位
BT2020、DRM blob/寄存器报文校验及退出 SDR 通过。
**显式 P010 的 HDMI HDR 没有通过**：开启和关闭新开关都为 P010→CLIENT→SDR HDMI，
两态 C2 输出元数据、逐帧 HDR 元数据/PTS、100 帧及 PixelCopy 统计完全相同。
这证明该下游限制在原转换路径同样存在；不是本次解包导致，也未被本次修复。
不能把原生 HDR 通过移用于显式 P010 的 HDMI HDR，或把 PixelCopy 当十位精度证据。

分项关闭恢复原解包及 CPU 工作量，其他选择保留；整包停用并重启恢复原 HWC 和六项
平台哈希，新增伴随库／核心不存在，新增属性清空；重启重新启用恢复加速。
boot、Mali 0.4.2、DVFS、外部 Zygisk 和 Frame Guard 的 0/60/60 保持。
网页 63 项、Android 隔离 18 项及安装包／嵌套组件／安装后挂载清单通过。

设备最终保持本项开启，新安装默认关闭。实际测试 ZIP SHA256：
`42f0f231a13e164a41516f76834a494f2a9eaaa88710dc0980a406dbfbd98cbe`。
安装包内保留安装前候选快照，使用本最终附录；限定实验结果不作为稳定版公开发布。

# 开关整合与 QMS 开销说明

本次整理只改变功能的组织和说明，不自动替用户选择一套新配置。原来的每个分项仍可单独关闭并重启回退。模块启动检查通过，只表示本次选中的组件和启动状态符合检查，不表示所有播放器、游戏、HDR 显示器都已通过。

| 主界面分组 | 通俗说明 | 通过范围与边界 |
| --- | --- | --- |
| 播放基础 | 硬件解码、图像处理、软件解码和像素转换的基础配套 | 仅应用实际调用的路径受影响；更新版本不等于所有视频更快 |
| 原生播放稳定性 | 暂停时等缓冲、恢复后继续出帧，退出时正确回收任务 | 指定 Exo 暂停恢复已有用户通过记录；后续版本另有探针和回退记录。快进索引修复独立在 LSPosed，不混算 |
| AV1 播放 | 合适的输出路径使用无损 AFBC，减少带宽；保留源胶片颗粒 | 指定路径有精度／回退记录，依赖消费者和驱动兼容，不承诺所有播放器零复制 |
| 十位画质与 HDR | 修正十位缓冲布局、HWUI 格式、SF 合成目标及 HDMI 元数据传递 | 指定 P010→十位 AFBC 的 PQ／HLG 路径已通过。HW/Main10 copy-back 还需客户端映射；未完成所有应用及显示器校色 |
| 显示兼容与合成 | 模式查找、非英语设置、HDR 状态、硬件图层和假音频拔线处理 | Auto 勾选及 HDR 默认显示用户已确认；固定模式持续锁定、明确 HDR 选择跨重启仍待验收，不能宣传短黑已解决 |
| QMS（验证中） | 同分辨率切帧率时保持 HDMI 链路，目标是减少换时序短黑 | 已首次绑定、原厂基线启用／恢复；持续播放故障仍修复中，HDMI 实屏无黑未验收 |

主界面前五组显示“已选／当前生效／重启后生效”的数量。半选表示原有分项组合，没有偷偷改成全开。半选组点击后选全组；全选组点击后关闭本组。开启组会补齐依赖，可能启用其他组里的基础项；关闭组只关闭它的成员，其他组选择保留，但依赖关闭后可能不再生效。操作后的联动提示列出新增依赖。

“分项与回退”默认折叠，内有原来的独立开关和 Codec2 后端选择。QMS 不属于任何批量开启组，避免一次“优化播放”就改变显示切换行为。整包停用仍按原模块流程重启恢复原固件对应路径。Mali 的内核／CSF 已作为配套组合管理；首次绑定涉及 boot，继续独立显示明确行为，不合并到普通用户态开关。

## 哪些旧提示已纠正

- 不再把已补齐 SF 十位目标的 HDR 合成写成“等待 SF／当前不生效”。说明改为实际通过的 P010、PQ／HLG、十位 AFBC 和回退范围，并保留未完成校色边界。
- 不再把已定位并有指定 Exo 暂停恢复通过记录的背压修复笼统写成“尚待首次验收”；明确用户反馈属于哪个范围，不把后续版本仅有探针记录说成全应用验收。
- HW/Main10 缓冲、HWUI、AFBC、EOS、元数据复用等不再只用“实验”代替说明；显示其作用、依赖和关闭结果。固件精确匹配检查保留。
- Mali g18 首次绑定、CSF fence 和 DVFS 写明已有启动／隔离负载／回退证据；游戏持续帧时间仍待对照，不能包装成所有游戏收益。
- QMS 继续标注验证中，不能因菜单能开启、日志无错或 ADB 投屏正常而改成“无黑已修复”。

## QMS 检测会不会消耗性能

会有成本，但要区分三类工作。

启动时的固件指纹、导出符号 CRC、模块配套和首次绑定检查，是启动资格检查，不会在每个视频帧重新计算文件 SHA。WebUI 没有定时后台刷新；打开、手动刷新和回到页面时读取状态。

切帧率时，需要等待真实 vblank、fence，并核对供电、链路、时序和 VTEM。这些检查负责避免提交在错误对象或帧边界生效，不能为了降低数字就跳过。分数时序如果硬件需要逐帧调整 VTotal，相关逐帧处理也不能直接删掉。

恒定输出时，硬件能重复同一时序和 VTEM。test8 的诊断实现仍逐帧走原厂提交，不仅增加工作，还把观察跨过两个真实 24Hz 帧当成 gate93 故障，反复恢复到 60Hz。新版候选只在切换阶段做提交；恒定、已完成且通过验证的状态不重提同一事务。线程等待新命令，最多每 100ms 做一次只读核对，收到命令立即唤醒。它不靠定时器伪造 vblank，也不补造漏掉的帧。

所以“输出 60 帧就做 60 次完整核对”不适合恒定阶段。候选目标是减少重复提交和抢锁，而不是关闭出错保护。100ms 是只读核对间隔，不是增加 100ms 的切换响应延迟；命令会唤醒线程。外部模式变更的已有生命周期／身份验证仍保留，低频核对不是新授权可以写入过期对象。

目前新版已通过实际 C 逻辑的隔离测试和匹配原 Image 的 74 项导出 CRC 核对；尚未完成新版在真实播放中的 CPU 时间、唤醒次数和锁竞争对比。当前设备旧 test8 在桌面／WebUI 空闲约 15.22 秒，同一 QMS 线程 CPU tick 增量为 0，只能表示这段空闲观察没有 tick 精度可见的增长，不代表播放、变速或新版候选零成本。不能把“检查次数减少”直接说成游戏帧率提升。后续用线程 CPU 时间及实际提交／保持计数做轻量观察，不运行额外 GPU 压测或截图干扰播放。

## 厂商实现如何处理

Rockchip 的 [dw-hdmi-qp QMS 提交 5a89a1cb8b9c](https://github.com/rockchip-linux/kernel/commit/5a89a1cb8b9c3cba5666151e838d2a3d760fe0ea) 在启用、变速、停用时安排工作队列，通过 `rockchip_hdmi_wait_vsync()` 等真实垂直同步推进阶段。恒定稳定阶段不需要持续重新提交同一套完整显示事务。

本项目参考的是这些具体行为，而不是声称所有 RK3588 项目都如此。分数帧率的 VOP2 时序处理另有配套，不把一个 HDMI 提交当成完整链路移植。厂商成套驱动直接访问自己匹配的结构和接口；当前固件缺少这些接口，专用 `.ko` 必须额外确认对象身份、ABI、所有权和恢复路径。启动身份校验因此仍需保留，稳态重复提交则可以减少。上游等待返回值的已知差异也没有照搬。

物理 HDMI 短黑是否消失，最终仍由显示器观察验收；日志只帮助判断发生了变速、恢复还是链路重建。

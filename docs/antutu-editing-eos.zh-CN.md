# 安兔兔 12.0.2：完整 4K Surface 剪辑流程的 EOS 对照

## 状态

此次完成了原厂对照与应用结束条件定位，**未完成可安全集成的系统修复**。
没有新增运行时补丁、改变媒体数据、修改跑分结果或发布新模块版本。
0.5.1 的停止崩溃修复与这里的剪辑提前结束是两条问题；不能将前者的验证当作后者通过。

## 方法与结果

使用同一个已安装官方测试应用、同一段 3840×2160、30 fps、450 帧、15 秒的 AVC 素材。
原厂对照关闭整个 decode-stack 后重启，核验原厂解码组件哈希。
两侧保持全局 Mali、系统、内核不变；未修改 Yamby 或 LSPosed。
因此这里的“原厂”指原厂解码栈，不代表恢复了所有设备组件。

| 条件 | 生成文件帧数 | 活动结束 | Codec2 服务 |
| --- | ---: | --- | --- |
| 用户问题现场，0.5.1 | 369 | 否，370/450 | 存活 |
| 原厂，正常调度 | 450 | 是 | 存活 |
| 原厂，投屏编码并行 | 450 | 是 | 存活 |
| 0.5.1，多轮正常及并行负载 | 多轮 450，另有一轮 449 | 是 | 存活 |
| 原厂，限时源回调线程调度压力 | 82 | 否，回放无法到达预期帧数 | 存活 |
| 原厂，移除调度压力后重测 | 450 | 是 | 存活 |

压力对照仅临时调整该测试源回调线程的 CPU 亲和性和调度策略，并施加一个 CPU 核的限时负载。
它用于暴露结束条件竞争，**不是日常性能成绩，也不等同于证明两套栈的失败概率相同**。
测试后清理负载并恢复日常模块配置；未将这些调度设置写入模块。

## 已定位的结束条件

剪辑应用的编码回调使用“已编码计数达到当前已解码计数”作为发送
`MediaCodec.signalEndOfInputStream()` 的条件，没有在这个条件中要求源解码 EOS。
当编码端短暂追上源回调时，应用可以在素材尚未处理完之前关闭编码输入。
编码回调还没有排除 `BUFFER_FLAG_CODEC_CONFIG` 的计数影响。

原问题日志中，MP4 封装器明确记录只编码了 369 帧，随后应用转而回放这个短文件；
源解码器在切换前没有报告输入 EOS。回放解码器正常报告了文件结束，
但应用仍使用 450 帧的预期完成条件，空输出／结束回调后不再继续处理。
这解释了 369 个实际视频帧加一次结束回调后显示 370/450 并等待。

原厂压力对照同样先结束编码，只生成 82 帧，随后回放遇到相同的完成条件缺口。
这证明新版 SDK 并不是触发这一类故障的必要条件。
新版与原厂在输出时序上仍可能改变触发概率；有限次数的正常结果不证明所有场景都安全。

## 系统模块边界

应用主动发送 EOS 表示不再提交输入。通用 Codec2／MPP 不能仅凭此请求判断
应用究竟已经完成工作，还是错误地提前结束。
在系统中忽略 EOS、按固定帧数延迟 EOS，或人为放慢编码来避开竞争，
会改变其他录制、转码与流式客户端的合法行为，不满足本项目的兼容性要求。
补帧、重复帧、缩短预期计数或仅让测试界面结束，也不构成保留全部内容的修复。

完整修复需要应用明确跟踪源 EOS，等待所有取帧／绘制任务提交完毕后才结束编码输入，
过滤配置包的帧计数，并以回放 EOS 正确处理完成与异常短文件。
这部分属于测试应用逻辑，当前没有改动官方 APK。

设备日志、APK、反汇编、媒体素材和设备专用脚本只保存在本地，不进入发布包。

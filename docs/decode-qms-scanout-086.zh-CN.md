# QMS 切换边界诊断：test17

这是针对剩余“无重建、整幅短黑”的定位版本，不是新增无黑修复。保留 test16，协议报文、通知等待、原厂提交／fence、位深和刷新策略均不变。

此前每启动最多 96 条边界记录常在用户操作前耗尽。test17 将边界诊断默认关闭，通过仅 root 可写的内部参数 `owner_boundary_limit` 限量开启；每启动硬上限 1024 条，测试工具只开启 96 条，结束后写回 0。稳态播放没有新增逐帧日志或工作线程，常规故障记录仍保留。

## 这次补齐的证据

- 切换前后的实际 VOP DSP_CTRL、VACT 和扫描行。DSP_CTRL 的 standby 描述符与 VACT 描述符都按原 Image 表逐项校验，不能套用新版内核结构。
- 写入 VTEM 的 M_CONST／Next_TFR 所在字之后，记录真实单调时间、DRM 帧号及扫描行；不改变写入顺序，不插入等待。
- 保留 GCP、HDCP2、VTEM、时序和调度器的旧边界记录，方便与用户实际操作关联。

原 Image 的 `vop2_crtc_standby` 和 `vop2_crtc_regs_dump` 增加完整指纹检查。SYS_STATUS0 的行号读取参考厂商 VOP2 的 `vop2_read_vcnt`，只在已限定的 RK3588 VOP 版本、端口、电源及原厂锁保护下读取普通状态寄存器，不读 IRQ 清除寄存器、像素缓冲或 HDCP 密钥。

参考厂商固定快照中的 [VOP2 实现](https://github.com/rockchip-linux/kernel/blob/77168c8d5ab82399f65a80e9f807b50ba37cf483/drivers/gpu/drm/rockchip/rockchip_drm_vop2.c)。本机旧内核没有独立的 `vop2_read_vcnt` 符号，不能声称直接调用了这个原厂函数；新增代码使用限定硬件上的普通 MMIO 读，结构偏移另按原 Image 验证。

## 证据的限制

扫描位置和时间戳说明软件何时写入发送寄存器，不能直接证明 HDMI 线上的 VTEM 发送时间或电视收到的字节。切换前后没有屏蔽位变化也不能排除两个采样点之间的瞬态。暂不解读缺少位定义的 QP packet-status 寄存器，不将寄存器名字当作发送确认。

若没有观察到输出屏蔽变化，再根据写入所在帧／扫描区域核对公告是否有完整发送机会；有证据后再选择单项修复。此前 END 位和四帧等待的负结果保留，不把它们改名重复计为升级。

## 集成和验证

Decode Stack `0.8.6-qms-test17-ddc1`；Mali Global `0.4.2-qms-test19` 仅增加对应精确配套，不更换 g18 GPU。新原生寄存器／生命周期代码在 Android 注入对象测试中通过 54 项，精确配套测试通过 15 项，功能模块导入 CRC 仍为 74 项。实际启动及用户 HDMI 观察另行记录，不用这些检查代替实屏验收。

安装保留两个模块备份、原 boot、DDC／声音修复、Auto/HDR、Zygisk/LSPosed 和 Frame Guard 关闭选择。停用显示项后重启及整包回退机制沿用现有实现。本轮不写 boot，不操作播放器，不截图。

## 直连实测结果

用户确认播放／暂停／步进仍黑。限量采集取得序号 26–49 的 96 条完整边界记录；DSP_CTRL 始终为同一值，standby 位为 0，VACT 保持起点 82、终点 2242。GCP 控制与 HDCP2 bypass 均未在采样点变化。24 次目标公告写入中，23 次在扫描行 82 之前，一次在第 125 行；不能由此把全部短黑归结为固定的公告迟到，也不能当作线端发送确认。

整段累计切换序号从 25 增至 50、帧错误为 0，只有 26–49 有完整边界记录，不外推序号 50。最终诊断额度为 0，临时 trace 实例已移除。启动检查后迟到确认计数由 0 增至 1，是 test16 路径的实际运行证据；因缺少窗口起点该计数和黑场精确时间，不称为某次黑场的逐次对照证明。短黑未根治。

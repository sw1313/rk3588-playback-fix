# Decode Stack 0.6.1：本地 AV1 十位输出路径验证

> 历史研发阶段记录；当前发布与最终 AV1 播放结果见 [0.6.3 报告](decode-av1-063.zh-CN.md)。

这是本地验证版本，公开项目 Release 仍以下载页为准。目标为契约匹配的
RK3588／Android 12 API32 固件。沿用原有 5.10.66 内核、boot、Mali、
Frame Guard、Yamby 原版组件和 LSPosed 0.3.3。

## 改动与原因

旧的 AV1 Surface 兼容路径统一转换为标准 P010。实测中它既增加格式转换，
又使显示端进入 RGB 合成。同一份 4096×2160 十位 AV1 本地文件，在复用
已安装 SmartTube 的 Amzn ExoPlayer 2.10.6 默认渲染器时，最终二进制对照中
360 帧丢了 299 帧。
此前的网络播放另有缓冲耗尽，不能混用网络和本地结果。

0.6.1 查询实际图形缓冲区的 consumer usage：

- RK3588 显示合成 Surface，且不是编码输入端：请求保留原生十位输出，
  交给 NV15 显示平面，避免 P010 转换和 RGB 合成。
- 纹理／ImageReader 等非显示合成消费端：使用硬件直出的标准 P010，
  导入前核对 mapper 的位深、位移、行距、色度偏移和分配大小。
- 原有缓冲区客户端保留完整精度的 NEON／标量复制路径。

应用显式要求标准 P010 时不选择 NV15；要求裁剪复制时保留原复制模式。
两种请求均通过 854×480 十位 AV1 的专门测试。

AV1 Main profile 同时涵盖八位、十位，不能只凭旧 profile 判断输出位深。
原生路径明确向 MPP 请求保留十位，八位码流仍由解析器输出八位。诊断中
未强制保留十位的旧请求曾得到 NV12；该快路径已排除，不能用来证明十位性能。

标准 P010 通过该固定 MPP／Codec2 配对的私有格式标志 `0x10000000` 协商。
这不是上游通用 MPP 格式。它只在 RK3588 十位 4:2:0、无 FBC／tile 时启用，
为现有 AV1 硬件后处理设置 P010 输出、字节行距及缓冲区边界。原生 NV15
显示路径不使用此标志。此改动不替换内核驱动，不调整频率。

## 本地测量

所有文件先传到盒子，性能测量不读取网络。长文件由短样片直接重复封装，
没有重新编码；不是新增的独立摄影素材。部分十位样片由 SDR 源转码或
合成图案生成，用于验证位深、吞吐和元数据，不能作为 HDR 摄影画质评价。

| 测试 | 结果 |
| --- | --- |
| 同一 Exo 引擎、同一 6 秒 4096×2160 AV1 十位文件 | 旧 P010 复制路径丢 299/360；新路径丢 9/360，位深保持十位 |
| 同步 MediaCodec、4096×2160 AV1 十位 60 秒 | 3600/3600，迟到超过 20ms 为 0，显示回调间隔 P95 为 16.667ms |
| 同一 Exo 引擎、4096×2160 AV1 十位 60 秒 | 显示 3590、丢 10；这轮全部丢帧发生在开始两秒内，之后无新增丢帧 |
| 同一 Exo 引擎、UHD60 PQ＋AAC，约 79Mbps、30 秒 | 1800/1800 显示，0 丢帧 |
| 同一 Exo 引擎、相同 AV1＋Opus 包无损封装 WebM、30 秒 | 1800/1800 显示，0 丢帧 |
| 本地 PQ／HLG | 完整输出；驱动报告 HDMI 十位、BT.2020；HDR 包 EOTF 分别为 2／3；退出恢复 SDR |
| 854×480 AV1 十位 | 显示 Surface 与标准 P010 ImageReader 均完整输出，验证非对齐宽度 |
| 非显示合成 ImageReader UHD 十位 | 标准 P010，360 帧、EOS、stop 完成 |
| 11 组独立软件参考逐样本对比 | AVC／HEVC 十位／AV1 八位与十位／VP9 十位全部精确相等 |
| AV1 八位、十位、全范围及 HEVC HDR／4K 的 5 组生命周期测试 | 暂停、seek、seek 后出帧、EOS 均通过 |
| 其他本地格式回归 | 16 条可用路径完整结束；AVC、HEVC、AV1、VP9、VP8、MPEG-2、H.263 及系统 MPEG-4 软解 |

驱动状态中，旧路径显示平面为 RGB，新路径为十位 NV15；AV1 时钟实测
396MHz。该对照将本次持续丢帧定位到十位输出／合成路径，不能据此断言
所有 RK3588 AV1 卡顿都有同一原因。HDMI 结果来自驱动状态及包寄存器读取，
没有外接 HDMI 分析仪，不作为完整线缆侧认证。

独立 Exo 程序从已安装 SmartTube APK 复用播放器引擎，预读上限为 64MiB／
5 秒，读取本地文件。它没有修改 SmartTube APK，也没有加载其完整 UI、
自定义 renderer 配置或网络链路。网络 SmartTube 的完整应用复测已执行，但未通过，详见下节。

## 保留的限制与回退

自制 AV1＋Opus MP4 在这份旧 Exo 默认封装路径下会停在播放时钟 0；
新旧输出路径均复现。同一音视频包无损改封装 WebM 后正常。这项不列入
模块修复通过清单，也没有修改播放器的 MP4 解析器。

`c2.rk.m4v.decoder` 在原有版本和本版均无法实例化；系统
`c2.android.mpeg4.decoder` 正常。不能将此测试项标为新增硬件格式支持。
标准 P010 纹理端不具备 NV15 显示平面的性能保证；所有分辨率、AV1 编码工具、
播放器组合也尚未穷举。现有 HDR4000 客户端合成限制仍按原报告保留。

```sh
su -c 'sh /data/adb/modules/rk3588_decode_stack/mode-control.sh av1_native off'
# 重启后恢复原有完整十位 P010 复制路径
su -c 'sh /data/adb/modules/rk3588_decode_stack/mode-control.sh av1_native on'
# 重启后按消费端选择原生输出
```

`av1_native` 依赖有效的 `codec2_sdk_next`；关闭依赖时抑制实际启用，保留选择。
`codec2_sdk_next off` 可退回 1.14.3 SIMD 核心，整包关闭可恢复原厂解码组件。
配置切换经过重启应用，不热替换已加载的库。

## SmartTube 完整应用实播复测（2026-10-16）

同一 COSTA RICA 视频的 AV1 701／3840×2160 60fps HDR 档位，
使用 0.6.1 实播仍持续掉帧：首段约 27.7 秒新增丢帧 331、显示 569；
后续约 31.6 秒新增丢帧 1557、显示 337。采样点缓冲为 1～5 秒，
日志也记录了期间缓冲耗尽，不能凭截图排除网络影响。

NV15 硬件显示平面与 HDMI 十位 BT.2020／ST2084 均已生效，
AV1 时钟为 396MHz。日志另外出现队列超时、解码器重建，
以及 flush／缓冲重新分配；尚未证明这些现象的具体因果关系。
本地合成／转码样片通过不代表完整 SmartTube 应用或该原始片源通过。
下一步下载同一 701 码流及音轨，不转码进行本地对照。

### 同一 YouTube 原始片源的本地复测

已完整下载该视频的 701 AV1 十位 HDR／3840×2160／60000÷1001 fps
及 251 Opus 音轨，仅无损改封装 WebM。移除容器差异产生的 AV1
时域分隔 OBU 后，编码视频哈希一致；音频哈希完全一致。
前 60 秒本地文件复用已安装 SmartTube 的默认 Exo 引擎，完整到达 EOS，
计数器为显示 858、丢帧 2739、跳关键帧 5 次，解码器只初始化一次。
十位 NV15 及 HDMI BT.2020／ST2084 路径生效。完整约 314 秒文件
随后已在盒子本地播放，初段也持续丢帧；整段最终统计尚未收集。

因此，先前生成样片的通过结果不能外推到这个真实 AV1 码流。
该片源的丢帧能够在不读取网络的情况下复现，排除了单纯网络加载解释；
尚待进一步区分码流处理、缓冲队列及出帧时序原因，不能宣称已修复。
本轮只安装独立诊断程序和复制媒体，没有修改解码模块、播放器或底层固件。

## Opus／MP4 时钟停在 0 的独立验证

旧默认 MP4 解析路径提供的 Opus 初始化数据只有一项，
OpusHead 中的 dOps 数值字段仍为大端排列；WebM 对照提供了正常
OpusHead、codec delay 和 seek preroll 三项。实测失败时音频已输入
255 个包但输出为 0，进度停在 0；同一音视频流改封装 WebM 可走时钟。

仅在独立诊断实例的 Extractor／TrackOutput 边界补齐初始化数据、
规范化头字段后，同一个 MP4 完整播放 30 秒：1800 输入，1797 显示，
启动丢 3 帧，时钟到达 30005ms，EOS 正常；音视频码流未改。
该补丁只验证解析路径，没有改已安装 SmartTube、Yamby 或 LSPosed，
也没有把应用解析器补丁伪装成系统 VPU 驱动更新。无损改封装仍是
当前不改播放器组件即可使用的解决办法。

## 真实 AV1 片源深入对照（2026-10-16）

完整 314 秒本地片源完成 EOS，显示 4405、丢帧 14403。
关闭音轨仍掉帧；直接同步 MediaCodec 的 60 秒测试完整解出 3597 帧，
但 3463 帧迟到超过 20ms，总用时约 62.96 秒，不能把完整解码当作流畅。
纹理端完整十位 P010 吞吐约 57.24fps；隔离额外 gralloc HDR 元数据写入后
约 57.41fps，标准 C2 HDR 信息保留，测试后恢复原开关。

直接 MPP／NV15 的 60 秒测试约 61.32fps；短段统计约 96% 时间等待
硬件任务完成，解析约 3%。600 次任务采样平均约 5949819 个周期，
在 396MHz 下约 15.02ms；平均 poll 等待约 15.18ms。
这些是当前库、寄存器配置和固件路径的计时，不是芯片不可改善的绝对上限。

| 完整十位实验（60 秒） | 显示 | 丢帧 | 结论 |
| --- | ---: | ---: | --- |
| 增加 8 个 Codec2 输出槽 | 957 | 2640 | 未达标，撤回 |
| 送包重试 500us，保持原超时预算 | 937 | 2660 | 未达标，撤回 |
| 同候选 3000us 对照 | 526 | 3071 | 未达标 |
| 临时将解码线程放到实际 A76 大核，不改频率 | 516 | 3081 | 未改善，恢复亲和性 |
| MPP 输入任务 4→12，包缓冲同步扩容 | 1310 | 2287 | 有限改善，仍未达标，撤回 |

不同轮次不是严格隔离的芯片性能排名；所有实验均未通过最终流畅性要求，
不能作为已修复或量产模块的新功能。实验没有更改丢帧阈值、像素或 HDR 内容。

整包停用后，原厂 MPP＋Codec2 播同一本地片段显示 3553、丢 43；
但 DRM 显示平面为 NV12，解码初始化行距为 3840，是八位输出，
虽然 HDMI 仍显示十位 BT.2020／PQ。不能把这个数字当作保留十位的性能通过，
也不能据此推荐全局回退并牺牲精度。完整十位路径为 NV15。

所有未达标的私有候选均退出生效配置，恢复原始 0.6.1 的核心及 MPP 包。
没有发布新的 Release，Yamby、LSPosed、Mali、boot 和内核保持原样。
后续目标应针对真实 AV1 的完整十位输出／硬件任务交付，而不是反复调码率或 CPU。

补充：同一真实 AV1 码流保持 MP4 封装并配 Opus，在独立实例应用
解析修正后，时钟到达约 60017ms、正常 EOS，但显示 1236、丢 2361。
因此修正 Opus 时钟不会自动解决真实 AV1 的持续掉帧。
最终已恢复 0.6.1 全部原始核心／MPP 哈希，退回 SDR，清理盒子临时
候选；下载的真实视频保留。开发目录重编译、剥离后的三份二进制也
与原 0.6.1 完全一致，避免后续误打包实验库。

# RK3588 Playback Fix · v0.8.6

**RK3588 播放、显示与游戏图形升级——分项控制，可回退。**

面向 **RK3588 播放与游戏图形链路**的可回退升级项目，包含系统解码／显示模块、全局 Mali 模块、播放器 LSPosed 客户端，以及可选的应用内 Vulkan 驱动。各组件独立安装，不要求全部开启。

项目已从早期的 Yamby HW+ 设置补全和固定 60Hz 规避，发展为系统组件协同升级：Decode Stack 负责解码、缓冲传递、HDMI／HDR；Mali Global 负责 GPU 用户态、配套内核／CSF 和响应／稳定性优化；LSPosed 客户端负责已适配应用的格式与索引修复。系统模块严格匹配固件，保留独立选择及重启回退。仓库名称沿用，方便旧链接和更新继续使用。

**0.8.6 正式版的主要变化：Auto 下保留已匹配的视频帧率，减少 Exo 播放器暂停、恢复、同片快进时不必要的显示模式切换。** 指定 Exo 场景已由用户在 HDMI 实际显示器上确认通过。原生队列报错与 MKV 快进回片头另有独立修复，三项不混算。

## 适用设备与安装前提

系统模块针对 **H96 Max V58／RK3588、Android 12／API32、指定 5.10.66 固件**适配。相同芯片或内核版本不代表兼容：安装器还检查固件文件哈希、ABI 和组件配套，未知版本会拒绝，不能绕过检查通刷。

- Decode Stack 和 Mali Global 需要可用的 root／模块管理环境；WebUI 需要 KsuWebUI 或提供兼容 root 接口的管理器。
- LSPosed 客户端需要已正常工作的 Zygisk／LSPosed。Yamby 设置适配当前对应 **2.1.0.11（20010012）**，应用升级可能需要重新适配。
- QMS 需要支持 QMS 的接收端、系统 Auto 和匹配的内核／启动配套。普通 VRR 支持不等于支持 QMS；矩阵、功放或转接器也会改变链路能力。
- 图形服务前首次绑定及低层显示功能需要单独准备匹配设备、固件和现有 root 的私有启动适配。**公开 ZIP 不包含 boot，也不会把任意设备自动适配为可用。** 涉及 boot 的操作与普通用户态开关分开处理。

## 安装与更新

1. 从 [DOWNLOADS.md](DOWNLOADS.md) 选择需要的组件，核对文件名和 SHA256。
2. 在模块管理器安装 Decode Stack／Mali Global ZIP。Decode 安装器检查依赖后处理重叠旧模块；不要再手动开启旧独立解码模块。全局 Mali 也不与旧按应用 Mali 实验叠加。
3. 打开模块 WebUI，查看当前配置与依赖。升级保留既有选择，不会因正式版更新就把全部功能开启；缺少私有启动配套的低层功能不能直接启用。
4. 保存选择后重启，再检查实际生效版本、启动检查和“待重启”状态。运行中的图形库不会被开关热替换。
5. 需要客户端功能时，安装 APK，在 LSPosed 启用并勾选对应应用，打开客户端设置选择所需修复，再强行停止并重开播放器。APK 版本号不是 LSPosed 框架版本号。

Mali 安装器从固定上游 HTTPS 地址下载闭源用户态驱动及所需 CSF，并检查大小和 SHA256；已有校验通过的本地缓存可用于重装。公共包不携带这两类闭源载荷。首次绑定的准备、启用及恢复步骤见 [启动适配说明](magisk-mali-global/boot/README.md)。

| WebUI 分组 | 主要功能 | 生效条件与边界 |
| --- | --- | --- |
| 播放基础 | MPP 硬件解码配套、RGA 图像处理、Codec2 兼容层、libyuv 和软件解码库 | 只影响应用实际使用的接口；不是把所有视频强制换成同一解码器 |
| 原生播放稳定性 | 原生 Surface 输出、暂停缓冲背压、所有权／退出保护、输出需求通知、HEVC EOS 任务回收 | 新核心等依赖由界面联动；保留原生输出，不以复制回退代替队列修复 |
| AV1 播放 | 原生输出、源胶片颗粒恢复、显示与纹理路径无损 AFBC | 兼容路径减少带宽和复制；不支持的消费者保留回退，不保证所有应用零复制 |
| 十位画质与 HDR | P010 布局与 SIMD／成对解包、导入复用、HEVC 十位直接显示、HWUI 十位映射、GPU 合成目标及元数据传递 | 保留完整精度；客户端缺 P010 映射时仍需客户端修复；完整显示校色未全部验收 |
| 显示兼容与合成 | 模式查找、系统分辨率／HDR 设置、帧率保留、缩放硬件图层、相同元数据复用、假音频拔线过滤 | 各项作用独立；减少 CLIENT 合成取决于真实图层条件，不强占硬件平面 |
| HDMI QMS | 同分辨率下真实刷新率切换 | 独立开关，不随其他分组全选；需接收端与私有启动配套，不覆盖所有格式切换 |

“分项与回退”中保留独立开关和 Codec2 后端单选：旧后端、1.14.3 SIMD、1.14.16。需要新版核心的分项会补齐依赖；选择较新后端并不表示所有场景必然更快。

组开关显示“已选／当前生效／重启后生效”的数量。“部分已选”表示保留自定义组合，点击会选全组；关闭组只关闭组内成员，其他组的选择保留，但可能因缺依赖暂停。“当前”是本次启动实际状态，“重启后”是保存配置；灰显不等于选择丢失。启动检查通过表示组件加载和依赖符合检查，不代替实际播放验收。中英文切换会记忆语言，不改变功能选择。

## Auto、帧率保留、QMS 和固定模式的区别

| 设置／功能 | 实际行为 |
| --- | --- |
| 系统 Auto | 允许系统按内容选择合适显示模式；桌面当前输出 4K60，并不代表 Auto 勾选已丢失 |
| 播放期间保持匹配帧率 | 同一视频图层暂停、恢复、同片快进时，保留已有有效片源请求，避免清零后反复切回桌面刷新率 |
| QMS | 对真正需要的同分辨率变速维持 HDMI 链路；不能代替帧率保留消除多余选模请求 |
| 固定分辨率／刷新率 | 目标是持续保持用户选定模式，Auto 才自适应；非英语识别已修正，所有固定组合长期锁定仍需分别验收 |
| Frame Guard（历史规避，已退出推荐组合） | 固定 60Hz 会阻止 Auto 内容匹配；当前已验收配置不再依赖它 |

0.8.6 的保留策略集成在系统 SurfaceFlinger 的共同图层入口，覆盖旧 Binder 和 BLAST 事务。它只在 Auto 下对同层符合条件的清零请求保留原值；**新正数帧率请求照常更新**。隐藏或移除图层由原生选模策略排除，不把上个视频的请求全局缓存给下个视频。关闭 `display_session` 并重启恢复原处理。

当前该功能依赖 `hwc_client_hdr10` 所在的系统加载配套；这属于本固件实现依赖，不表示帧率保留只支持 HDR。QMS 有自己的独立开关和配套检查。

**播放器开超帧／插帧会怎样？** 如果播放器把输出请求从 24／30fps 更新为 60fps 等新正数值，策略会放行更新；系统仍按显示能力和原生选模规则选择输出，可能使用片源整数倍刷新率。如果播放器插帧后仍上报原始帧率，Auto 可能继续依据旧请求选模，影响插帧收益。这种组合尚未专门实测，不能承诺自动识别所有超帧功能。

本版指定 Exo 场景在 Frame Guard 关闭条件下实屏通过，不能扩展为所有播放器／接收端均无黑场。换分辨率、SDR／HDR 信号格式切换、中间设备重训仍可能短黑。详见 [实现、实际命中及验收边界](docs/decode-refresh-session-086.zh-CN.md)。

直连显示还有独立的 EDID／E-DDC 修复：原厂读取第 2／3 扩展块时存在分段访问错误，会丢失真实接收端能力，不能用伪造设备库或强制 HDR 标志代替。Decode Stack 的精确内核配套修正读取，并在启动时通过原厂路径初始化显示。指定直连场景已有出画面和声音恢复记录，不能把这项基础连接修复等同于短黑修复。[直连修复与回退](docs/decode-ddc-direct-hdmi-086.zh-CN.md)。

## 十位 HDR、HW 绿屏与 HW+ 的关系

十位输出要贯通解码缓冲、客户端格式、GPU 合成目标、分配器、HWC 和 HDMI。仅让电视出现 HDR 标志，或仅把输出设置为十位，都不能证明整条链路正确。

本项目已记录指定显式 P010／PQ／HLG → 实际十位 AB30 AFBC 扫描输出、混合 SDR UI 和回退结果。完整 HDR 色彩校准仍未完成；灰阶参考曾有最多 3／3／4 码值偏差，不能标成逐码 RGB 完全一致。[物理 HDR 验证](docs/decode-physical-hdr-081.zh-CN.md)。

| 播放器选项 | mpv 路径 | 含义 |
| --- | --- | --- |
| HW | `mediacodec-copy` | 硬解后复制回系统内存，再渲染；需要正确的十位格式映射和布局 |
| HW+ | `mediacodec` | 硬解 Surface 路径，通常避免回读复制 |
| SW | `no` | 软件解码 |

HW 和 HW+ 都是硬解，HW+ 不是额外画质等级。指定 Main10 HW 问题包含系统缓冲布局与客户端缺 P010 映射两个断点：Decode Stack 提供系统修复，LSPosed 0.3.7 在原 ARM64 库哈希匹配时加载配套客户端修复。指定画面与暂停／快进已有记录，不涵盖所有绿屏原因。

Codec2 HDR10+ 桥只传递标准逐帧元数据，不代表已支持 HDMI 原生 HDR10+。当前也不提供杜比视界／LLDV／FEL 全链路升级。

## LSPosed 客户端：作用与使用

| 选项 | 作用与限制 |
| --- | --- |
| Yamby 默认解码补上 HW+ | 补全应用原有默认设置并保存；播放菜单仍可选 HW／HW+／SW，不修改 `vo` 或强制切换 `gpu`／`gpu-next` |
| 其他 mpv 播放器硬解优先 HW+ | 仅 RK3588，识别支持的常见接口并保留明确 SW 请求；纯 native／混淆封装不保证覆盖 |
| Yamby HW+ 灰白边修正 | 默认关闭，按实际解码裁剪与纹理尺寸补偿填充边；信息不匹配则跳过，不放大画面 |
| Main10 HW 十位回读修复 | 默认关闭，依赖系统十位缓冲修复和匹配 ARM64 原库；保留 HW 和 P010 精度，关闭后重开恢复原库加载 |
| Exo 多级 SeekHead 快进修复 | 默认关闭，匹配 Yamby APK 后读取真实 MKV Cues，处理指定片源快进回片头；不是系统刷新率钩子 |

Yamby HW+ 默认入口为“设置 → MPV 播放器 → 默认解码方式”。Yamby 设置补全不限芯片，APK 最低 Android 8.0；但具体解码能力由设备决定，其余适配有 RK3588／应用／库检查。LSPosed 作用域以已验证应用为准，不勾选 Android 系统进程。各项修改后重开播放器；未适配应用不能仅加入作用域就视为兼容。

## Mali Global 与游戏目标

Mali Global 管理全局 ARM32／ARM64 **g18p0 用户态**、可选匹配 KMD／CSF、图形服务前首次绑定、DVFS 和 CSF 同步稳定性。当前主线保留 g18，不把 g25 当成已完成升级。

- 用户态、内核／CSF、DVFS、同步稳定性分别控制，依赖联动且可重启回退。保存不实时切换驱动。
- 首次绑定在图形服务启动前把配套驱动绑定到 GPU，避免运行中交接；需匹配私有 boot，保留原 root 和外部 Zygisk。启动／回退记录包含 Zygisk Next 两个 ABI 与 LSPosed。
- DVFS 选项把负载检测周期从 100ms 改为 20ms，保留 OPP、电压、频率边界和温控。已有有界 GLES 突发负载收益记录，不等于所有游戏 FPS 提升。
- CSF fence 修复处理 metadata 引用的同步顺序，属于稳定性修复。曾被否决的 CSF 调度 tick 100→20ms 与 DVFS 不同，不作为当前优化交付。
- 《传奇四叶草》和 Eden 仍是实际游戏重点，持续帧时间、温度、功耗与原厂 g13 对照不能由启动成功推定通过。PanVK 另由应用内选择，长期稳定性仍属实验范围。

详见 [Mali 模块说明](magisk-mali-global/README.md)、[DVFS 验证](docs/mali-dvfs-031.zh-CN.md)、[CSF 同步修复](docs/mali-csf-fence-042.zh-CN.md) 和 [主要目标清单](docs/main-goals-priority.zh-CN.md)。本版不是整套 HWC／Composer 或 VOP2／HDMI 内建内核替换。

## 关闭、回退与故障处理

| 操作 | 回退结果 |
| --- | --- |
| Decode 分项关闭并重启 | 对应组件恢复升级前路径；其他已选项可能因依赖关闭而暂停 |
| Decode 整包停用／卸载并重启 | 恢复原固件解码／显示路径；独立 LSPosed、Mali 和 Frame Guard 不由它代管 |
| Mali 内核选原版并重启 | 恢复原 KMD／CSF，用户态选择独立保留；首次绑定启用时同时遵循启动适配恢复流程 |
| Mali 整包停用并重启 | 按已准备的独立启动恢复机制回到原驱动路径；备份不依赖模块自身目录 |
| LSPosed 关闭修复并重开应用 | 恢复对应原应用处理；也可停用模块作用域 |
| PanVK 切回 System GPU Driver | 退出游戏、切回系统驱动后重开；不需要改全局模块 |

**旧用户移除 Frame Guard 时，不能只禁用模块：这不会撤销已写入系统的刷新率值。** 先用它的“操作”恢复／暂停，或卸载恢复模块仍持有的值，再确认不再固定 60Hz。原值备份在 `/data/adb/rk3588-frameguard/original.conf`，之后的手动设置会受保护。当前正式版验收配置保持它 disabled＋paused；新安装无需再装。

启动检查失败时先读模块状态、依赖及回退记录，不反复强开或绕过指纹保护。涉及内核硬挂或 boot 写入中断，独立恢复机制也不能保证网络 ADB 可救援，可能需要断电或物理 Loader；具体边界见启动适配文档。

## 性能开销与验证范围

固件 SHA／ABI 配套主要在安装和启动检查，不逐帧重算。帧率保留随请求事件执行，无新增逐帧轮询线程；临时请求追踪默认关闭。QMS 在真正切换时等待真实 vblank／fence 并核对状态，稳定阶段保持硬件输出，不反复提交同一完整事务；保留最多每 100ms 的只读核对，命令会立即唤醒，不是强加 100ms 切换延迟。分数时序的必要逐帧处理不能省略。

这不等于零成本，也不代表已证明游戏性能提升；真实播放 CPU 时间、唤醒和锁竞争需另行量测。[开关与 QMS 开销说明（含历史阶段）](docs/decode-controls-and-qms-cost.zh-CN.md)。

| 已记录的结果 | 不应据此推定的结果 |
| --- | --- |
| 指定 Exo 原生队列暂停／恢复修复、指定 MKV 索引快进恢复、0.8.6 同片帧率保留实屏通过 | 所有片源、应用或电视都无报错／无黑场 |
| 指定 P010 十位扫描、精度及回退检查 | 所有 HDR 色彩校准、动态 HDR 和杜比链路通过 |
| g18 配套、启动、双 ABI 注入、CSF／DVFS 有界检查 | 所有游戏净收益、长期稳定性及 g25 兼容已通过 |
